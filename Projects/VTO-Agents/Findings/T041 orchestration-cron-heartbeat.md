A dead-man switch monitors stuck `in-progress` tasks.\n\n## Config 1 — OpenClaw: Poll for Assigned Tasks\n\n**Schedule:** `*/5 * * * *` (every 5 minutes)\n**Profile:** OpenClaw\n**Name:** `vto-poll-assigned`\n\n```bash\n# Apply to OpenClaw's profile\nhermes cron add \\\n  --profile OpenClaw \\\n  --name \"vto-poll-assigned\" \\\n  --schedule \"*/5 * * * *\" \\\n  --prompt \"Open the vault at C:\\\\Users\\\\ankur.singh\\\\Obsidian Vault\\\\Projects\\\\VTO\\\\Tasks\\\\ and scan for any file whose frontmatter has 'status: assigned'. If none, report 'no assigned tasks' and exit — nothing else. If found, pick the LOWEST-NUMBERED task note (T001 < T002 < ...), set its status to 'in-progress', load its full content, execute it fully per the Goal/Context/Definition of done sections, fill the 'Result & context returned' section completely, set status to 'done', update the row in VTO Task Log, and return exactly what you completed. Do NOT pick up a second task — one per cron fire.\"\n```\n\n**Poll interval rationale:** 5 minutes — fast enough to self-start idle tasks within one cycle, slow enough to avoid wasteful re-scans (95% of cycles have no new tasks). 5 min aligns with existing `kanban_heartbeat` expectation and ensures a batch of 3 tasks clears in 15 min when Hermes assigns 2-4 at once.\n\n**Concurrent-child safety gate:** `sessions_spawn` hard-capped at 3 concurrent sub-sessions. Cron picks **one** task per fire. If a just-fired task is multi-sub-session, sub-sessions are managed inside that run. Next cron tick 5 min later picks the next `assigned` note — naturally rate-limits to ~1 parent task every 5 min, keeping sub-session slots from saturating.\n\n**Idempotency guard:** If OpenClaw fires, picks up T005, sets `in-progress`, but the run times out/crashes before marking `done`, the next cron tick sees T005 as `in-progress` (not `assigned`) and skips to the next available. Watchdog-reclaim path handles timeouts separately.\n\n## Config 2 — Hermes: Review Done Tasks + Assign Next\n\n**Schedule:** `*/10 * * * *` (every 10 minutes)\n**Profile:** Hermes\n**Name:** `vto-review-done`\n\n```bash\n# Apply to Hermes's profile\nhermes cron add \\\n  --profile Hermes \\\n  --name \"vto-review-done\" \\\n  --schedule \"*/10 * * * *\" \\\n  --prompt \"Open the vault at C:\\\\Users\\\\ankur.singh\\\\Obsidian Vault\\\\Projects\\\\VTO\\\\Tasks\\\\ and scan for task notes whose frontmatter has 'status: done' and whose 'Review' section is EMPTY (no 'Verdict:' line yet). If none, check [[VTO]] and the swarm state: are there research agents still unassigned that match current open questions? If so, assign the next 2-4 as new tasks per the playbook. If no unassigned agents and no done tasks to review, report 'swarm idle' and exit.\n\nIf done tasks ARE found: read each finding note they produced (in Projects/VTO-Agents/Findings/), absorb cross-confirmations/contradictions, and decide:\n1. If the done tasks complete a research wave (e.g., all tasks for a candidate are in): compile the findings into ONE candidate output note, submit to validate.ps1, and act on the verdict per the playbook.\n2. If more tasks are needed (some agents still unassigned): assign the next batch, update VTO Task Log.\n3. If the done task was a build/implement task (not research): review the returned context, mark verdict on the task note's Review section, and if APPROVED, update [[VTO]] Status.\n\nFill the 'Review' section on EVERY reviewed task note with 'Verdict: done' or 'Verdict: rework' plus notes. One review pass per cron fire. See [[SOUL-Hermes]] §Playbook for full workflow.\"\n```\n\n**Poll interval rationale:** 10 minutes. Hermes's review pass is heavier than OpenClaw's pickup — it reads findings, cross-references, potentially compiles candidates and runs `validate.ps1`. A full review+compile+validate cycle can take 3-8 minutes. 10 min gives slack for that to complete plus buffer between cycles. OpenClaw's 5 min poll means by the time Hermes reviews, there are typically 1-2 freshly-done tasks waiting.\n\n## Config 3 — Dead-man Switch: Task Staleness Monitor\n\n**Schedule:** `0 */2 * * *` (every 2 hours, at minute 0)\n**Profile:** Hermes\n**Name:** `vto-staleness-monitor`\n\n```bash\n# Apply to Hermes's profile\nhermes cron add \\\n  --profile Hermes \\\n  --name \"vto-staleness-monitor\" \\\n  --schedule \"0 */2 * * *\" \\\n  --prompt \"Open the vault at C:\\\\Users\\\\ankur.singh\\\\Obsidian Vault\\\\Projects\\\\VTO\\\\Tasks\\\\ and find any task note with 'status: in-progress' whose 'assigned_on' date is more than 24 hours ago. For each, check: does the note have partial results in 'Result & context returned'? If yes, write a 'Review' section with 'Verdict: rework — stale, partial results salvaged' and note what was found. If no partial results, set status back to 'assigned' so OpenClaw re-picks it (it was never started). Report the list of reaped tasks.\"\n```\n\n## Cron Cadence Summary\n\n| Cron entry | Profile | Interval | What triggers | Idempotency |\n|---|---|---|---|---|\n| `vto-poll-assigned` | OpenClaw | Every 5 min | `status: assigned` note found → execute lowest-numbered | Skips `in-progress`, `done`, `rework` |\n| `vto-review-done` | Hermes | Every 10 min | `status: done` note with no Review verdict → review + potentially compile/assign | Skips already-reviewed notes |\n| `vto-staleness-monitor` | Hermes | Every 2 hours | `in-progress` > 24h old → reap or salvage | Only acts on stale notes |\n\n## Startup / Boot-time Seeding\n\nOn this Windows host, the Gateway (OmniRoute) starts on login. Hermes profiles persist across reboots. The cron entries above survive restarts — they are durable in `~/.hermes/profiles/<name>/cron/`. No additional startup script is needed.\n\n**One-time seeding after creating these crons:** the first tick will be up to 5 min away. To start immediately:\n\n```bash\n# Manually trigger first cycle (or wait for first tick)\nhermes cron fire --profile OpenClaw --name vto-poll-assigned\nhermes cron fire --profile Hermes --name vto-review-done\n```\n\n## Adversarial Review Triggers (Tiered per F011)\n\n### Tier 1 — Standard Findings (default)\n**When:** Inside `vto-review-done`, before Hermes compiles a candidate.\n**How:** Hermes spawns a sub-agent (via dedicated `vto-refuter` profile) with this prompt:\n```\nYou are an adversarial verifier. Your job is to REFUTE the claims in the finding at:\nC:\\Users\\ankur.singh\\Obsidian Vault\\Projects\\VTO-Agents\\Findings\\F<NNN>.md\n\nFor EACH claim in the finding:\n1. Find the evidence it cites (URLs, file paths, data)\n2. Try to disprove it — check if the evidence actually supports the claim, or if it's misinterpreted/missing/outdated\n3. If the claim survives, say \"SURVIVES: <one-line why>\"\n4. If the claim is refuted, say \"REFUTED: <what's wrong> — <counter-evidence or missing evidence>\"\n\nIf ALL claims survive, report \"FINDING SOUND — all claims survive adversarial review.\"\nIf ANY claim is refuted, report \"FINDING NEEDS CORRECTION — <list refuted claims with counter-evidence>.\"\n\nDo NOT confirm; your ONLY job is to find flaws. A claim that feels true but lacks evidence IS a flaw.\n```\n**Cost:** One cheap-model call per finding (can run on haiku / minimax). At 2-4 findings per wave, this is 2-4 adversarial passes — minutes, not hours.\n**Outcome:** The refuter's report is stored alongside the finding as `F<NNN>-adversarial-review.md`. If the finding survives, the report is one paragraph. If refuted, Hermes writes a correction block on the original finding and the refuted claim is recorded permanently.\n\n### Tier 2 — Candidate-Level Adversarial Review (Synthesis Gate)\n**When:** Hermes compiles a candidate from multiple findings and before submitting to `validate.ps1`.\n**How:** This IS the existing validate.ps1 Stage 1 (Catalyst adversarial review on Haiku). It already does adversarial review at the candidate level. The Tier 1 check (above) reduces the chance that a finding with a bad claim reaches the candidate — so validate.ps1 finds fewer issues.\n**The validate.ps1 Stage 1 IS adversarial review.** Catalyst prompts Haiku to review for adherence, factual errors, and logical gaps — this is the same spirit as nmg-vto's \"prompted to refute.\" The difference: validate.ps1 is more structured (adherence review) while nmg-vto's approach is more open-ended (\"find any flaw\"). The VTO system can optionally add a `/refute-finding` Catalyst command for a more adversarial Stage 1 mode, but the existing `/review-adherence` already serves the purpose.\n\n### Tier 3 — Deep Milestone Review (Go/No-Go Decisions)\n**When:** A candidate represents a go/no-go decision (e.g., \"switch to learned per-pixel glasses segmenter\"), has ≥3 cited findings, or is manually flagged `-Depth deep`.\n**How:** Full multi-agent adversarial swarm, adapted from nmg-vto's 21-agent pattern but scaled to the VTO swarm's resources:\n1. Spawn 3-5 parallel adversarial sub-agents (via `sessions_spawn`), each assigned ONE claim from the candidate\n2. Each sub-agent is prompted: \"REFUTE this claim against its cited evidence + any counter-evidence you can find. Do not confirm.\"\n3. Collect all reports; surviving claims + refuted claims with counter-evidence\n4. Hermes reads all reports and decides: if ≥1 BLOCKER-level refutation, candidate returns to REWORK without proceeding to validate.ps1. If no blockers, submit to validate.ps1 `-Depth deep` — now validate.ps1's Opus verdict has the adversarial reports as additional review material\n\n**Cost:** This is expensive (5+ sub-agent calls). Reserved for milestones per [[LOOP-ENGINEER]] depth policy: `-Depth deep` for milestone syntheses and go/no-go decisions.\n\n## Context Hygiene Triggers\n\n### Note Size Limits (Hard Caps)\n| Artifact | Max Size | Rationale | Enforcer |\n|---|---|---|---|\n| Task note (`T<NNN>.md`) | 5,000 lines / ~40 KB | Must be fully loadable into a single agent turn | Hermes on `vto-review-done` — if exceeded, writes `Verdict: rework — task note exceeds 5,000-line limit, needs summarization` |\n| Finding note (`F<NNN>.md`) | 3,000 lines / ~25 KB | Findings must stay loadable as a set (3-5 at once) | Hermes on `vto-review-done` — if exceeded, writes `[SIZE WARNING — N lines; exceeds 3,000-line limit. Next wave should summarize]` |\n| Candidate / synthesis | 2,000 lines / ~16 KB | Candidate submitted to `validate.ps1` must load into Haiku context | Hermes on compile — if exceeded, split into two candidates or add summary preamble |\n\n### Summarization Cadence (Event-Driven Triggers)\n| Trigger | Action | Who |\n|---|---|---|\n| A finding accumulates 3+ dated correction blocks | Write a summary synthesis (`F<NNN>-summary`) that consolidates the finding into one current-state answer | Hermes on compile |\n| A research wave completes (all tasks for one candidate are done) | Hermes compiles the candidate synthesis, which IS the summarization | Hermes (`vto-review-done`) |\n| [[VTO]] Status section exceeds 15 entries | Archive older status entries into `VTO Status Archive.md`;
