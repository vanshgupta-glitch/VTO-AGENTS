All flows follow OKF format and integrate with the [[LOOP-ENGINEER]] validation gate (`catalyst-env\\\\vto\\\\validate.ps1`).\n\n## 1. Swarm Firing Cycle\n\n### 1.1 Hermes Picks Agents\n- **When**: Hermes reads `[[VTO]]` + identifies open questions\n- **How**: Choose which research agents in `Projects/VTO-Agents/Research Agents/` matter now\n- **Scope**: Start with 2-4 agents, not all 11 (per SOUL-Hermes playbook step 1)\n- **Output**: List of agent files to assign\n\n### 1.2 Assign Tasks\n- **When**: Hermes decides which agents to fire\n- **How**: For each chosen agent, create task note `Projects/VTO/Tasks/T<NNN> <agent-id>.md`\n- **Template**: Use task note template with Context: *"Load `Projects/VTO-Agents/Research Agents/<file>.md` as your mission brief; deliver per its Output contract."*\n- **Set**: `status: assigned`\n- **Update**: [[VTO Task Log]] index row with task number, status, and brief citation\n- **Idempotency**: Task number T<NNN> is the idempotency key\n\n### 1.3 Kanban Board Mirroring (Assign)\n- **Command**: `hermes kanban --board vto create \"T<NNN> <title>\" --body \"Task note: Projects/VTO/Tasks/T<NNN>…md\" --created-by hermes --idempotency-key T<NNN>`\n- **Never set an assignee** — assigned ready card gets auto-executed by dispatcher; OpenClaw works from vault\n- **Card title**: `T<NNN> <short-name>` matching the task note\n\n### 1.4 Fire OpenClaw\n- **When**: Hermes instructs after assigning all tasks\n- **How**: *"Work the assigned VTO research tasks — spawn one sub-session per task, max 3 concurrent."*\n- **Tool**: `sessions_spawn` — one sub-session per assigned research task\n- **Concurrency**: Max 3 simultaneous sub-sessions; each collects before closing\n- **Sub-session prompt**: *"You are the research agent defined in `<full path to Research Agents/<file>.md>` — read it and execute it fully; write your finding note per the Output contract."*\n\n### 1.5 Sub-Session Execution\n- **When**: OpenClaw spawns sub-sessions for parallel tasks\n- **Each sub-session**:\n  1. Loads its research agent brief (SOUL-*.md or Research Agents/<file>.md)\n  2. Executes the mission completely\n  3. Writes finding after EACH answered question (frontmatter `status: draft`, update as you go)\n  4. An abort must never lose work; respawn continues from existing draft, never restarts\n  5. Max 10 minutes before hard-abort\n- **Output per sub-session**: `Projects/VTO-Agents/Findings/F<NNN> <topic>.md` in OKF `type: finding` format\n  - Question / Answer / Evidence (with URLs) / Implications for VTO\n\n### 1.6 Hand Back to Hermes\n- **When**: All sub-sessions complete and results returned\n- **How**: OpenClaw fills each task note's "Result & context returned" section:\n  - Links the finding notes (F<NNN> <topic>.md)\n  - Summarizes key results and context\n  - Notes any blockers or issues\n- **Set**: `status: done` on each task note\n- **Update**: [[VTO Task Log]] index row for each task\n\n### 1.7 Hermes Absorbs Findings\n- **When**: Tasks returned with finding notes\n- **How**: Hermes reads each finding note in `Projects/VTO-Agents/Findings/`:\n  - Cross-links contradictions and confirmations between findings\n  - Checks REFUTED-CLAIMS.md register (see Flow 5) before accepting any claim\n  - Records any new refutations in the register\n  - Synthesizes what was absorbed into emerging candidate\n\n### 1.8 Compile Candidate\n- **When**: Hermes has absorbed all findings from current wave\n- **How**: Synthesize absorbed knowledge into ONE candidate output note:\n  - Could be a finding synthesis, decision draft, or deliverable write-up\n  - Follow OKF format with proper frontmatter\n  - Cite all contributing finding ids\n  - Store as temporary candidate for validation gate\n\n### 1.9 Submit to Validation Gate\n- **When**: Candidate compilation complete\n- **How**: `catalyst-env\\\\vto\\\\validate.ps1 -File \"<candidate>\"`\n  - `-Depth standard` (default) for normal candidates\n  - `-Depth deep` for milestone syntheses, go/no-go decisions, or ≥3 cited findings\n- **Pipeline**:\n  1. Stage 1a: Import candidate into Catalyst DB (cheap model Haiku)\n     - Generates theory ID: `T_YYYYMMDD-HHMMSS-XXXXXX`\n  2. Stage 1b: Catalyst review (cheap model)\n     - Runs `review-adherence` (standard) or `review-theory` (deep)\n     - Generates review IDs: `R_YYYYMMDD-HHMMSS-XXXXXX`\n  3. Stage 2: Claude Opus final verdict\n     - Reads: GUIDANCE.txt, theory.md, review report(s)\n     - Decides: APPROVED or REWORK\n     - Outputs markdown verdict with basis and rework instructions\n     - Exit 0 = APPROVED\n     - Exit 2 = REWORK\n     - Exit 1 = pipeline error\n\n### 1.10 Act on Verdict\n- **When**: validate.ps1 returns\n- **Exit 0 (APPROVED)**:\n  - Write into `[[VTO]]` (Status + Decisions)\n  - Cite finding ids in Decisions section\n  - Update VTO.md status\n  - Cite verdict file path\n- **Exit 2 (REWORK)**:\n  - Copy numbered rework instructions from verdict into a NEW task note for OpenClaw\n    - Each item states: WHAT is wrong, WHERE, acceptance criterion for the fix\n    - Set status: rework (or assigned with rework instructions)\n  - Hermes updates Task Log with new rework task\n  - OpenClaw fixes EXACTLY the numbered items\n  - After fix: re-submit candidate to validation gate (re-loop)\n- **Never write unvalidated conclusions into [[VTO]]**\n\n### 1.11 Board Mirroring (Verdict)\n- **When**: Hermes acts on verdict\n- **Commands**:\n  - `hermes kanban --board vto comment <card-id> \"REVIEWED: <done|rework> — <one line>\"`\n  - Card id found by its T<NNN> title\n  - One-line status: "done" or "rework"\n\n### 1.12 Repeat\n- **When**: Research needs not yet met OR build tasks remain\n- **How**: Hermes decides next action:\n  - If research needs remain: pick next set of agents, go to Flow 1.1\n  - If build tasks remain: shift swarm from research agents to build tasks (per SOUL-Hermes step 8)\n\n## 2. Rework Cycle\n\n### 2.1 Validation Returns REWORK\n- **When**: validate.ps1 exits with code 2\n- **What**: Verdict markdown contains `VERDICT: REWORK` section with numbered rework items\n- **Each item has**:\n  - **WHAT**: What is wrong (specific defect)\n  - **WHERE**: Where in the code/plan it exists\n  - **Acceptance criterion**: What must be true for the fix to be accepted\n\n### 2.2 Hermes CreatesRework Task\n- **When**: Verdict is REWORK\n- **How**: Hermes creates new task note `Projects/VTO/Tasks/T<NNN> <something>-rework.md`\n- **Set**: `status: rework`\n- **Context**: Load the rework instructions from the verdict\n- **Update**: [[VTO Task Log]] with new rework task\n- **Kanban**: `hermes kanban --board vto create \"T<NNN> <something>-rework\" --idempotency-key T<NNN>`\n\n### 2.3 OpenClaw Fixes Rework Items\n- **When**: OpenClaw picks up rework task (status: rework)\n- **How**: Fix EXACTLY the numbered items — each has an acceptance criterion\n- **Rule**: Meet the acceptance criterion for each item, cite the evidence in the task note, change nothing else\n- **After fix**: OpenClaw sets `status: done`, updates task note with "Fix applied per validation verdict"\n- **Re-submit**: Candidate re-submitted to validation gate (go to Flow 1.9)\n\n### 2.4 Refutation-Recorded Rework\n- **When**: Rework item challenges a previously accepted claim\n- **How**: Check REFUTED-CLAIMS.md register first\n- **If claim appears in register**: Cite the register entry; do not re-litigate\n- **If claim not in register**: New refutation; record in REFUTED-CLAIMS.md before proceeding\n\n## 3. Critic Adversarial Review Flow\n\n### 3.1 Tier 1 — Standard Finding Review (Before Candidate Compilation)\n- **When**: Hermes plans to cite a finding in a candidate compilation\n- **How**: Hermes spawns a sub-agent (dedicated `vto-refuter` profile or Hermes clone) with prompt:\n  ```\n  You are an adversarial verifier. Your job is to REFUTE the claims in the finding at:\n  C:\\Users\\ankur.singh\\Obsidian Vault\\Projects\\VTO-Agents\\Findings\\F<NNN>.md\n  \n  For EACH claim in the finding:\n  1. Find the evidence it cites (URLs, file paths, data)\n  2. Try to disprove it — check if the evidence actually supports the claim, or if it's misinterpreted/missing/outdated\n  3. If the claim survives, say \"SURVIVES: <one-line why>\"\n  4. If the claim is refuted, say \"REFUTED: <what's wrong> — <counter-evidence or missing evidence>\"\n  \n  If ALL claims survive, report \"FINDING SOUND — all claims survive adversarial review.\"\n  If ANY claim is refuted, report \"FINDING NEEDS CORRECTION — <list refuted claims with counter-evidence>.\"\n  \n  Do NOT confirm; your ONLY job is to find flaws. A claim that feels true but lacks evidence IS a flaw.\n  ```\n- **Cost**: One cheap-model call per finding (haiku / minimax-m3:cloud)\n- **Outcome**: Report stored as `F<NNN>-adversarial-review.md` alongside the finding\n- **If finding survives**: Hermes proceeds; the finding is sound\n- **If finding needs correction**: Hermes writes a correction block on the original finding (not silent rewrite); refuted claim is recorded permanently\n\n### 3.2 Tier 2 — Candidate-Level Adversarial Review\n- **When**: Hermes compiles a candidate from multiple findings and before submitting to validate.ps1\n- **How**: This IS the existing validate.ps1 Stage 1 (Catalyst adversarial review on Haiku)\n- **Difference**: validate.ps1 is more structured (adherence review) while Tier 1 is open-ended \"find any flaw\"\n- **Optional**: Add `/refute-finding` Catalyst command for more adversarial Stage 1 mode\n- **Existing**: `/review-adherence` already serves the adversarial purpose\n\n### 3.3 Tier 3 — Deep Milestone Review (Go/No-Go Decisions)\n- **When**: Candidate represents go/no-go decision, has ≥3 cited findings, or manually flagged `-Depth deep`\n- **How**: Full multi-agent adversarial swarm, scaled to VTO resources:\n  1. Spawn 3-5 parallel adversarial sub-agents via `sessions_spawn`\n  2. Each sub-agent assigned ONE claim from the candidate\n  3. Prompt: \"REFUTE this claim against its cited evidence + any counter-evidence you can find. Do not confirm.\"\n  4. Collect all reports; surviving claims + refuted claims with counter-evidence\n  5. Hermes reads all reports and decides:\n     - If ≥1 BLOCKER-level refutation: candidate returns to REWORK without proceeding to validate.ps1\n     - If no blockers: submit to validate.ps1 `-Depth deep` — Opus verdict has adversarial reports as additional review material\n- **Cost**: Expensive (5+ sub-agent calls); reserved for milestones per depth policy\n\n### 3.4 Refuted-Claims Register\n- **File**: `Projects/VTO-Agents/Findings/REFUTED-CLAIMS.md` — permanent register\n- **Format**: Table with columns: Date | Finding | Claim | Why refuted | Refuter\n- **When any agent proposes a claim**: Must check this register first\n- **If claim appears**: Cites the register entry rather than re-litigating\n- **If claim not in register**: New refutation recorded before proceeding\n\n## 4. Validation Gate Integration Flow\n\n### 4.1 Candidate Submission\n```
catalyst-env\\vto\\validate.ps1 -File "C:\\Users\\ankur.singh\\Obsidian\\Vault\\Projects\\VTO\\Findings\\F003-frame-detection-removal.md" -Depth standard
```
\n- **Default**: `-Depth standard` (Stage 1b: review-adherence)\n- **Milestone**: `-Depth deep` (Stage 1b: review-theory + full Opus verdict)\n\n### 4.2 Pipeline Details\n- **Stage 1a** (import): Candidate copied to Catalyst DB `inbox/`; theory ID generated\n- **Stage 1b** (review): Catalyst runs review skill on theory ID; review IDs recorded\n- **Stage 2** (verdict): Claude Opus reads guidance + theory + reviews; decides APPROVED/REWORK\n- **Verdict format**: `# Validation Verdict — <name>\nVERDICT: APPROVED   (or: VERDICT: REWORK)\nTHEORY-ID: <tid>\n## Basis\n<3-8 bullets: which review findings upheld/overruled and why>\n## Rework instructions for Hermes\n<num items: WHAT, WHERE, acceptance criterion. Omit if APPROVED.>\n- **Exit codes**: 0 = APPROVED, 2 = REWORK, 1 = pipeline error\n\n### 4.3 Gates Recursive Behavior\n- **If APPROVED**: Write into VTO.md, cite verdict file. Done for this cycle.\n- **If REWORK**: Copy rework instructions → new task for OpenClaw → re-loop from Flow 2.3\n- **If pipeline error (exit 1)**: Debug the validation pipeline; do not proceed until resolved\n\n### 4.4 Validation Gate History (VTO Project)\n- **2026-08-04**: CANDIDATE-frame-detection-removal → REWORK (3 items)\n- **2026-08-04**: Haiku deep-review REWORK → 3 rework items confirmed applied\n- **2026-08-04**: CANDIDATE-frame-detection-removal-v2 → APPROVED (3 passes completed)\n- **Verdict file**: `catalyst-env\\\\vto\\\\validation-reports\\\\20260804-120108-CANDIDATE-frame-detection-removal-v2-FINAL.verdict.md`\n\n## 5. SOUL Document Integration\n\n### 6.1 SOUL-Hermes (Orchestrator)\n- Governs the swarm firing cycle (Flow 1)\n- Manages validation gate integration (Flow 4)\n- Acts on verdicts (Flow 1.10)\n- Maintains "state of knowledge" summary in [[VTO]]\n- Writes everything in OKF ([[OKF-FORMAT]])\n\n### 6.2 SOUL-OpenClaw (Worker)\n- Executes tasks and research missions (Flow 1.4-1.6)\n- Writes findings per Output contract (Flow 1.5)\n- Handles rework tasks (Flow 2.3)\n- Saves incrementally (frontmatter `status: draft`)\n- OKF everywhere; cite or it is opinion\n\n### 6.3 SOUL-Critic (Adversarial Reviewer)\n- Performs Tier 1, 2, 3 adversarial reviews (Flow 3)\n- Maintains REFUTED-CLAIMS.md register\n- Documents refutation outcomes per output contract\n- Produces critic-<topic>.md findings + critic-landscape.md rollup\n\n## 7. ## 9. Agent Work Report Flow (added 2026-08-24)

- **When**: Any agent completes or fails a task — swarm loop, vault research loop, or the vto-research heartbeat.
- **Rule**: Post a compact work report (task id, executor, outcome, finding/artifact links, verdicts, anything skipped) to the agent's DEPARTMENT channel under its own bot identity — in addition to the originating-channel reply and the admin verdict. The admin check stays; what was checked becomes visible to the human in the loop.
- **Channel map**: per [[AGENT-PROFILES]] §1 — researcher → #swarm-research, coder/openclaw/opencode → #swarm-code, critic → #swarm-critique, admin/deploy → #swarm-admin, build/lint/test → #swarm-tests, video → #swarm-video, accuracy → #swarm-accuracy.
- **Mechanism**: shared post_queue (gateway posts, rate-guarded). Swarm loop: `postWorkReport()` in `apps/daemon`. Vault loops: `npx tsx scripts/agent-report.ts --agent <role> --channel <swarm-*> --file <report.md>`.
- **Full spec**: [[ORCHESTRATION-DIAGRAM]] §"Work reports".
- **Amended 2026-08-24 (later same day)**: the report is TWO posts per task — a start report at claim time (":inbox_tray: starting — task <id>") and the completion work report. Daemon: `postStartReport()` + `postWorkReport()`.
